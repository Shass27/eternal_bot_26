# 10. Nav2 (autonomous navigation)

> **Concept**
> - **Nav2** takes a goal pose and drives the robot there: a *planner* draws a global path on the map, a *controller* follows it while avoiding what the lidar sees, and *behaviors* (spin, back up, wait) recover when stuck. A behavior tree (`bt_navigator`) sequences them.
> - **Nav2 needs three inputs that already exist:** a map (`/map`), the transform chain `map → odom → base_link`, and a laser scan (`/scan`). It adds no localization of its own here: slam_toolbox in localization mode (chapter 9) supplies `/map` and `map→odom`, so there is **no map_server and no AMCL**.
> - **Two costmaps.** The *global* costmap (whole map, static layer + obstacle layer + inflation) is for planning. The *local* costmap (3 m × 3 m rolling window around the robot) is for the controller. Inflation grows lethal cells outward so the planner keeps the robot's centre away from walls.
> - **The robot is holonomic.** The controller is **MPPI with `motion_model: Omni`**, which samples `vx`, `vy` and `wz`, so the robot strafes. A DWB / differential setup would never use `vy`.
> - **Nav2 does not talk to the wheels directly.** Its velocity command passes through a smoother and a collision monitor, then twist_mux (priorities and e-stop), and only then reaches `/cmd_vel` and the MecanumDrive plugin.

## What was done, by phase
1. **Pick the localization source.** The stock Nav2 launch starts `map_server` + `amcl`. Here slam_toolbox already publishes `map→odom` and `/map`, so only the *navigation* half of Nav2 is started (`navigation_launch.py` from `nav2_bringup`, not `bringup_launch.py`). Two nodes publishing `map→odom` would fight.
2. **Parameters.** `config/nav2_params.yaml` is the stock Jazzy file, tuned for this robot (table below).
3. **Command chain.** Nav2's default output topic `cmd_vel_nav` is the *input* of `velocity_smoother`, so the collision monitor cannot also write it (that is a loop). The collision monitor writes **`cmd_vel_safe`** instead, and `twist_mux.yaml` lists `cmd_vel_safe` as its priority-10 navigation input:
   ```
   controller_server -> cmd_vel_nav -> velocity_smoother -> cmd_vel_smoothed
                     -> collision_monitor -> cmd_vel_safe -> twist_mux -> /cmd_vel -> ros_gz_bridge -> MecanumDrive
   ```
   All hops are plain `geometry_msgs/Twist`, which is what the bridge expects (`use_stamped: false` in twist_mux).
4. **Startup ordering.** `launch/nav.launch.py` first runs a small python process that waits until `map→odom` can be looked up, and only then includes Nav2 (via an `OnProcessExit` handler). Without this the global costmap cannot find the `map` frame in time and the lifecycle manager aborts the whole bringup.
5. **Re-map with margin.** The first `obs_map` was cropped right at the spawn point. The costmap is the size of the SLAM map, so the robot started on its edge ("Robot is out of bounds of the costmap"). `obs_map2` was re-mapped with 0.5 m of margin south of spawn.

## Params changed from stock
| Where | Setting | Value | Why |
|---|---|---|---|
| frames (`bt_navigator`, costmaps, `collision_monitor`, ...) | `robot_base_frame` / `base_frame_id` | `base_link` | This robot has no `base_footprint`. |
| `controller_server` `FollowPath` | `motion_model` | `Omni` | Mecanum can strafe. |
| `FollowPath` | `critics` | `PreferForwardCritic` dropped | Omni has no preferred direction. |
| `controller_server` | `min_y_velocity_threshold` | `0.001` | Otherwise sideways commands are treated as zero. |
| `velocity_smoother` | `max_velocity` / `min_velocity` | `[0.5, 0.5, 2.0]` / `[-0.5, -0.5, -2.0]` | `vy` enabled; it is zero in a diff-drive setup. |
| both costmaps | `robot_radius` | `0.30` | Circular footprint around the 0.44 m wheelbase. |
| both costmaps | `inflation_radius` / `cost_scaling_factor` | `0.50` / `3.0` | The start-strip gap in the arena is about 0.8 m, so a larger inflation would close it. |
| `collision_monitor` | `cmd_vel_in_topic` / `cmd_vel_out_topic` | `cmd_vel_smoothed` / `cmd_vel_safe` | See phase 3. |

Other values worth knowing:
- Planner: `NavfnPlanner` (`GridBased`) followed by `SimpleSmoother`.
- Controller runs at 20 Hz; goal tolerance is 0.25 m and 0.25 rad (`general_goal_checker`).
- MPPI: `time_steps: 56`, `model_dt: 0.05` (a 2.8 s horizon), `batch_size: 2000`, `vx_max: 0.5`, `wz_max: 1.9`.
- Both costmaps use `/scan` as their observation source.

## Running it
Nav2 needs the sim *and* SLAM in localization mode running first.
```bash
ros2 launch eternal_bot_description gazebo.launch.py world:=arena_obs   # T1; wait for the spawn
ros2 launch eternal_bot_description slam.launch.py                      # T2; mode: localization on obs_map2
ros2 launch eternal_bot_description nav.launch.py                       # T3; logs "waiting for map->odom", then starts Nav2
rviz2 -d src/eternal_bot_description/config/gazebo.rviz --ros-args -p use_sim_time:=true   # T4; Fixed Frame: map
```
In RViz use **2D Goal Pose** to send a goal. Teleop (`key_teleop`, priority 20) overrides Nav2 (priority 10) while a key is held; `/e_stop` blocks both. See `commands.md`, sequence F.

## Checking it works
```bash
ros2 lifecycle get /controller_server                  # active (also: planner_server, bt_navigator, behavior_server ...)
ros2 topic echo /cmd_vel_safe --field linear           # non-zero while navigating
ros2 topic info /cmd_vel -v                            # only twist_mux should publish
ros2 topic echo /collision_monitor_state               # the collision monitor's action state (name set in nav2_params.yaml)
```
Judge motion against sim-time ground truth, not wall-clock (see `.claude/rules/sim-launch.md`, "Debugging motion").

## Gotchas
- **`slam.launch.py` must be in localization mode, with a map path that exists.** `mapper_params_online_async.yaml` has `mode: localization` and an **absolute** `map_file_name` that currently points to a path on the original author's VM (`/home/parallels/...`). On any other machine edit it to your checkout's `maps/obs_map2_serial` (no extension) or the map never loads and Nav2 never starts.
- **Nav2 sits at "waiting for map->odom".** SLAM is not running, or its start pose does not match the spawn. See chapter 9, *Start pose matters*.
- **"Robot is out of bounds of the costmap".** The costmap extent comes from the SLAM pose graph. Re-map with margin around the spawn (that was `obs_map2`).
- **The robot ignores goals but `/cmd_vel_safe` moves.** Something with a higher priority is holding the mux: a latched `/e_stop` (`data: true`) or a publisher on `cmd_vel_emergency`. Release with `ros2 topic pub --once /e_stop std_msgs/msg/Bool '{data: false}'`.
- **Publishing to `cmd_vel_nav` by hand does nothing useful.** It is the smoother's input; test the mux with `cmd_vel_safe`.
- **Raw `/cmd_vel` bypasses everything.** A bypassing publisher (chapter 9, "Two ways to drive") competes with twist_mux; do not use it during navigation.
- **Every Nav2 node needs `use_sim_time: True`.** `nav.launch.py` passes it; set it yourself for anything you start by hand.
- **One TF publisher per link.** The MecanumDrive plugin owns `odom→base_link` and slam_toolbox owns `map→odom`. If `robot_localization` is added, disable one `odom→base_link` source.
- **Wheel-slip drift.** Rollers are friction-emulated, so `odom` drifts on strafes and spins; the controller works in the corrected `map` frame, but a long fast strafe can still overshoot the goal tolerance.

## Files
| File | Role |
|---|---|
| `launch/nav.launch.py` | Waits for `map→odom`, then includes `nav2_bringup` `navigation_launch.py` with our params, sim time on |
| `config/nav2_params.yaml` | Stock Nav2 params tuned for the mecanum robot |
| `config/twist_mux.yaml` | `cmd_vel_safe` (10) < `key_vel_filtered` (20) < `cmd_vel_emergency` (255), plus the `e_stop` lock |

| `maps/obs_map2.{pgm,yaml}`, `obs_map2_serial.{posegraph,data}` | Map and pose graph Nav2 plans on |
